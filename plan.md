# Multi-Board Multi-App Architecture Plan

## Goals

- Keep board support, application behavior, and LVGL presentation as separate layers.
- Make every board and app dependency explicit and reproducible.
- Reject unsupported board and app combinations during configuration.
- Keep all source-code comments in English.
- Preserve a predictable workflow on macOS, Linux, and Windows.

## Architecture Rules

### Board Layer

Each `boards/<board>/` directory owns only hardware-specific material:

- The board BSP and on-board hardware driver dependencies.
- GPIO and capability definitions in `board_config.h`.
- Partition layout and board-specific sdkconfig defaults.
- `supported_apps.txt`, the source of truth for board and app compatibility.
- An English `README.md` documenting the SoC, memory, display, touch controller,
  GPIO map, buses, sensors, storage, audio, PMU, BSP package, limitations, and
  supported apps.
- The board README must include this GPIO allocation table:

  | GPIO | Signal/Function | Peripheral/Sensor | Bus | Direction | Shared/Conflict | Source |
  |------|-----------------|-------------------|-----|-----------|-----------------|--------|

  Include every occupied GPIO, associate each signal with its sensor or
  peripheral, and identify shared, multiplexed, boot-strapping, or otherwise
  constrained pins. Use `N/A` rather than omitting a field. Every row must be
  traceable to an official schematic, BSP definition, datasheet, or explicit
  user-provided custom-board specification.
- The board README must also list on-board sensors or peripherals that do not
  consume an ESP GPIO directly, with their controlling bus, address or chip
  select, interrupt/reset signals when applicable, and a reference to the GPIO
  table rows.

Application libraries such as image decoders, MP3 decoders, and application-only
protocols must not be declared by a board component.

### Application Layer

Each `main/app_<name>/` directory becomes a selected ESP-IDF component and owns:

- Its CMake source list and public/private include paths.
- Its `idf_component.yml` application dependencies.
- App-specific lifecycle, FreeRTOS tasks, error handling, and model adaptation.
- The bridge between reusable logic and `lvgl/<name>` model APIs.

The top-level build registers only the selected app directory. Non-selected app
components and their dependencies must not be installed or built.

The ESP-IDF `main` component automatically depends on every built component.
Therefore, selected app components must not declare a dependency on `main`, which
would create a dependency cycle. Keep generic startup and orchestration in `main`,
and place reusable services that app components consume under `components/`.

### Common Main Layer

Files directly under `main/` must be board-independent and reusable. They may
contain generic startup, service coordination, and interfaces, but not one app's
assets, screen logic, file paths, or fixed sensor policy.

During migration:

- Move one-app-only helpers into the owning `main/app_<name>/` component.
- Move helpers shared by multiple app components into a normal component under
  `components/` so dependencies remain acyclic.
- Keep `app_main()` ownership and the selected-app interface explicit.

### LVGL Layer

`lvgl/<name>/` owns screens, widgets, styles, assets, and UI-facing model APIs.
It must not initialize a BSP, mount storage, start hardware drivers, or own board
selection. App logic posts data through the LVGL project's model interface and
obeys LVGL locking requirements.

### Dependency Ownership

- `boards/<board>/idf_component.yml`: BSP and on-board hardware only.
- `main/app_<name>/idf_component.yml`: app-only libraries such as
  `esp_lv_decoder`, MP3 decoding, and app-specific protocols.
- `main/idf_component.yml`: dependencies required by generic startup only.
- `components/<service>/idf_component.yml`: reusable service dependencies.
- `dependencies.lock`: generated by ESP-IDF Component Manager; never edit it by
  hand.
- `managed_components/`: generated and ignored; never use direct edits as the
  durable implementation. Use a version-controlled local component override or
  a maintained fork for required BSP patches.

## Target Layout

```text
boards/<board>/
|-- CMakeLists.txt
|-- idf_component.yml
|-- board_config.h
|-- supported_apps.txt
|-- sdkconfig.board
|-- partitions.csv
`-- README.md

main/
|-- CMakeLists.txt
|-- idf_component.yml
|-- <generic startup and orchestration>
`-- app_<name>/
    |-- CMakeLists.txt
    |-- idf_component.yml
    |-- README.md
    `-- <app-specific sources and headers>

lvgl/<name>/
|-- inc/
|-- src/
`-- assets/

components/<shared_service>/
|-- CMakeLists.txt
|-- idf_component.yml
|-- include/
`-- src/
```

## Implementation Phases

### Phase 0: Protect the Current Baseline

- [ ] Record successful board and app builds before moving files.
- [ ] Convert the local AMOLED 2.06 display-buffer changes in
  `managed_components` into a version-controlled override or fork.
- [ ] Confirm the selected BSP version and ESP-IDF version for each board.

### Phase 1: Add Compatibility Metadata

- [ ] Add `supported_apps.txt` to every board directory.
- [ ] Make top-level CMake reject an incompatible `BOARD` and `LVGL_PROJECT`.
- [ ] Make `switch_board.sh` and `switch_board.bat` read the same compatibility
  files after board selection.
- [ ] Show every app in the selector and suffix unsupported entries with
  `(Incompatible)`; do not allow accidental selection.
- [ ] Keep `board_config.h` compile-time capability flags aligned with the board
  README and compatibility list.

### Phase 2: Make Apps Independent Components

- [ ] Add `CMakeLists.txt` and `idf_component.yml` to every `main/app_<name>`.
- [ ] Register only `main/app_${LVGL_PROJECT}` in the top-level build.
- [ ] Move app-only source files and dependencies to the owning app component.
- [ ] Move cross-app services from `main/` to version-controlled components when
  an app component must consume them.
- [ ] Define a small selected-app interface for generic startup and shutdown.

### Phase 3: Correct Dependency Ownership

- [ ] Move `esp_lv_decoder` from the board manifest to the slide-player app.
- [ ] Move the Helix MP3 dependency to the salary-cat app.
- [ ] Keep QMI8658 with the board only if it is treated as an on-board device;
  otherwise declare it in the app or shared sensor service that consumes it.
- [ ] Keep BSP-transitive dependencies out of app manifests unless an app uses
  their public API directly and needs an explicit component contract.
- [ ] Regenerate and review `dependencies.lock` through Component Manager.

### Phase 4: Stabilize LVGL Integration

- [ ] Give every LVGL project an explicit public UI/model header.
- [ ] Keep widget and asset changes inside `lvgl/<name>`.
- [ ] Keep hardware initialization and FreeRTOS orchestration in the app layer.
- [ ] Update root CMake and both selector scripts when adding an LVGL project.
- [ ] Document required board capabilities for every app.

### Phase 5: Documentation and Validation

- [ ] Add the required English README to every board and app component.
- [ ] Verify that every board README maps all occupied GPIOs to the corresponding
  sensor or peripheral and documents shared or constrained pins.
- [ ] Build every compatible board and app pair in an isolated build directory.
- [ ] Verify that every incompatible pair fails during CMake configuration.
- [ ] Validate partition tables and binary size for every board.
- [ ] Perform hardware smoke tests for display, touch, storage, sensors, audio,
  and PMU features used by each compatible app.

## Acceptance Criteria

- Adding a board does not install app-only dependencies.
- Adding an app does not modify an unrelated board manifest.
- A selected app is the only app component included in its build.
- Selector labels and CMake validation agree for all board and app pairs.
- Deleting `managed_components/` and rebuilding does not lose project fixes.
- All compatible combinations build from a clean checkout.
- All source comments and newly added project documentation are in English.
